## 开场（00:00 – 01:30）

**小舟**：大家好，欢迎回到《元数据夜话》。现在做 AI 应用的团队，都在干同一件事——给模型喂领域知识。最省事的做法是把文档切碎了做 RAG；讲究一点的，会搭一个结构化的知识库。但只要你的领域稍微结构化一点，比如数据治理这种，马上就会撞上一个老问题：这些知识，到底该长成什么形状？是老老实实建一套 ER 表，还是织成一张图？今天我们请到的老麦，为这个问题吵了一整年，最后干脆不吵了——跑了个体测。

**老麦**：大家好，我是老麦。我自己维护一个数据治理的开源工具，叫 govio。这个问题我的立场肯定是图这边，但今天我不想只讲立场，我带了一份数据：同一套元数据，装进两种形状，让同一个模型去做题，二十三道题，六个题型，硬碰硬跑了一遍。

**小舟**：先别剧透结论，咱们按顺序来。不过我可以先给听众挖个坑——你待会儿会看到一个特别反直觉的结果：图并没有让模型「更对」，但是让它「更省」。这个「省」是怎么回事，就是今天的主线。

## 第一幕：领域 Agent 的公式（01:30 – 04:30）

**小舟**：先对齐一下语境。你说的「领域 Agent」，到底是个什么东西？

**老麦**：现在构建一个专业领域的 Agent，本质上就是三样东西的组合：**专门的信息、技能、Runtime**。技能就是 CLI、各种工具调用；Runtime 就是 Codex、Claude Code 这些 agent 运行时。这三样里，Runtime 和技能其实都是「买」得来的——现成的、成熟的。

**小舟**：真正买不来的呢？

**老麦**：是**信息层**。领域独有的、通用模型不知道的那些事实。而且信息层里最有设计含量的，不是「存什么」，是「以什么形状组织」——形状直接决定了 Agent 能以多高的效率和质量去用它。

**小舟**：拿你的数据治理场景举例子？

**老麦**：治理信息有两类来源。一类是**原生结构化**的：表、字段、类型这些元数据，直接从数据库里抽，机器生成，天然靠谱。另一类是**非结构化**的：业务关系、指标口径、数据标准，散落在文档和人脑子里。这类现在流行的做法是用 JSON Schema 约束 LLM 的抽取输出，人工审核后入库——格式由 schema 保证，事实由人保证，边界很清晰。

**小舟**：所以问题就变成：这两类信息汇合之后，存成什么、怎么查？

**老麦**：对。这就是今天全部争论的起点。两条路：一条是正经的 ER 建模——每类实体一张表，外键串起来；另一条是把信息织成图——节点是实体，边是关系。注意，我们说的「图」不是指必须买一个图数据库，而是一种**逻辑模型**，这个待会儿展开。

## 第二幕：治理问题的本质是「关系」，不是「记录」（04:30 – 08:30）

**小舟**：你文章里有一句话我印象很深：治理信息的本质是关系，不是记录。展开讲讲。

**老麦**：你听几个真实的治理问题就知道。第一个：改这张表的某个字段，会影响哪些下游指标？第二个：这个数据标准被哪些列遵循了？还有哪些缺口？第三个：这个派生指标的口径，往上追经过了哪些原子指标、哪些物理列？

**小舟**：这三个问题的共性是什么？

**老麦**：它们全是**路径问题**，而且路径长度未知。改一个字段，影响可能一跳就到，也可能穿三层派生指标才到。如果你用「记录」的思维去回答——就是 ER 的思维——每类问题都得定制一套 JOIN，问题越开放，SQL 越复杂；路径深度一变，查询就得重写。

**小舟**：图这边呢？

**老麦**：图这边，同一个问题**始终是一次遍历**。比如刚才那个问题，用 Cypher 写出来就是：从物理表出发，沿着 HAS_COLUMN 走到列，指标通过 REFERS_COLUMN 指到这一列，再沿着 DERIVED_FROM 星号 0 到 3 跳，把上游指标全捞出来——一行 MATCH，完事。那个「星号 0 到 3」就是变长路径，路径多深是原生的语法，不用你改写查询。

**小舟**：而且返回的东西也不一样，对吧？

**老麦**：这是我认为更关键的一点。SQL 返回的是**扁平行集**——表和表 JOIN 完之后，所有东西摊平成一行一行。图返回的是一张**子图**：相关的表、列、指标和它们之间的关系，一次性以原本的结构呈现。你想想 Agent 的工作记忆是什么——就是上下文窗口。扁平行集回来，还得写代码重组一遍才能塞进 prompt；子图回来，序列化一下**直接就是 prompt 上下文**，而且恰好是回答这个问题所需的最小上下文，token 消耗随遍历深度线性可控。

**小舟**：所以你有个说法叫「两个维度相乘」？

**老麦**：对。**查询自然度 × 返回形状**。查询自然度：把「找出生效日期影响的下游指标」翻译成多层 JOIN，模型要做大量关系代数推导，容易错；翻译成 MATCH 模式，几乎是把问题里的名词换成节点标签、动词换成边类型——映射距离越短，生成正确查询的概率越高。返回形状：子图直接进上下文。两个维度是乘法关系，任何一个是零，体验就崩。

**小舟**：先等等，我先替 ER 阵营把话接过去，这正好是下一幕。

## 第三幕：反方陈述——认真回答「存进 SQLite 不行吗」（08:30 – 13:00）

**小舟**：（笑）老麦，恕我直言，你前面这段听着像图数据库的广告。咱们认真点：正经的 ER 模型，为每类实体建正经的表，用外键表达关系——落到你这个治理场景，大概几张表？

**老麦**：六到八张带约束的表。核心的比如：physical_table 存表，col 存列、外键指回表，metric 存指标，然后两张关联表——metric_ref_column 表达指标引用了哪些列，metric_derived_from 表达指标之间的派生关系。

**小舟**：这套方案的优势，你如实说。

**老麦**：如实说，优势很实在，有三条。第一，**物理层一致性**：外键约束在数据库层面就保证了引用完整性，图这边只能靠导入逻辑自律。第二，**点查和固定一两跳查询极快且直白**：「表有哪些列」「指标定义是什么」，SQL 三行搞定，比 Cypher 还顺手。第三，**单文件、零依赖，SQL 生态成熟**——这个不用多讲。

**小舟**：那如果我的问题主要就是一两跳的固定查询，ER 模型是不是完全够用，甚至更好维护？

**老麦**：**是，我承认。**这一点文档里写得明明白白：固定一两跳，ER 甚至更好维护。分歧出现在**开放的多跳异质路径**上。还是那个问题：「派生指标经过哪些原子指标和物理列」——ER 模型要上递归 CTE，再加多表 JOIN；而且每增加一种实体类型，查询就要大幅改写。图那边呢？一行 MATCH，路径长度随手改，穿越几种实体都不影响写法。

**小舟**：你把这总结成过一个概念，叫「认知负荷分配」？

**老麦**：对，我列过一张六维度的对比表，我口头过一遍：
- **固定一两跳查询**：图顺手，ER 更顺手，SQL 更直白——ER 胜；
- **异质多跳、深度不定**：图一行 MATCH，ER 要递归 CTE 处理异质分支，或者在应用层拼接——图胜；
- **返回形状**：图天然子图直接进上下文，ER 是扁平行集要应用层重组——图胜；
- **模型演化**：图加个标签就行，无 DDL；ER 每个新实体等于新表加迁移，动态属性要么宽表要么 EAV——图胜；
- **一致性约束**：ER 有物理外键，图靠导入逻辑——ER 胜；
- **Agent 的 schema 对齐成本**：图只需要知道标签和边类型，ER 要理解多张表的外键拓扑——图胜。

**小舟**：四比二。但你也别高兴太早——这是纸面推演。你们不是跑了个体测吗？拿出来晒晒。

## 第四幕：Benchmark 是怎么设计的（13:00 – 16:00）

**老麦**：好，上数据。设计很简单：**同一份元数据，装进两种形状**。一份是 SQLite 的 ER 库；另一份是 govio 的图库，Cypher 查询。数据规模：**19 个数据源，2594 张表，48807 个字段**——是一个真实企业环境抽出来的量级。

**小舟**：谁来答题？

**老麦**：同一个执行模型，deepseek-flash。两个条件唯一的差别是知识库形状加一份配套的说明文档：SQLite 条件给它 sqlite-schema.md，描述表结构；图库条件给它 govio 的 schema.md，描述节点标签和边类型。其他全部对齐。

**小舟**：题目呢？

**老麦**：二十三道题，六个题型：**lookup**（点查）、**filter**（过滤）、**aggregate**（聚合）、**multi_hop**（多跳）、**open_ended**（开放题）、**negative**（负例题，专门测「该拒答时拒不拒」）。比如负例题会问一张根本不存在的表，看它编不编。

**小舟**：怎么算分？

**老麦**：每道题有一组检查项，答对得分，这是「检查项得分」——衡量事实正确性。然后再乘一个**简洁度权重**：答案在 300 字符以内，简洁度满分；超了就按 300 除以字符数折算，最多扣 20%。也就是说，**同样的正确度，啰嗦要扣分**。

**小舟**：为什么把「啰嗦」当负分？这不是惩罚认真吗？

**老麦**：因为我们测的是 Agent 场景，不是报表场景。Agent 的每一轮输出都是上下文成本——多余的解释、冗余的列、重复的查询结果，全都在消耗工作记忆和 token。所以口径是「达成目的且简洁」，没达成目的的不因简洁加分，达成了的话，越省越好。

## 第五幕：总分拆解——图没有「更对」，但是「更省」（16:00 – 21:00）

**小舟**：报总分吧。

**老麦**：图库 **0.867**，SQLite **0.827**。执行成功率，图库 22/23，SQLite 21/23。图库小胜。

**小舟**：四分的差距……说实话，以图吹了这么多年的架势，这差距听起来不算大。

**老麦**：所以要看拆解，拆开之后才是真故事。我先把最反直觉的结论放这儿：**两边的检查项均分，是完全一样的，都是 0.942。**

**小舟**：等等——事实正确性打平了？！那总分的差是从哪来的？

**老麦**：全部来自输出量。图库平均输出 **633.6 字符**，SQLite 平均输出 **996.4 字符**——SQLite 多了大约 57%。简洁度一个是 0.599，一个是 0.406。你拿公式验算一下：0.942 乘上各自的简洁度权重，一边 0.867，一边 0.827。**差的那 0.04，纯粹是简洁度差。**

**小舟**：那 0.942 的打平，内部构成呢？不会是每道题都一样吧。

**老麦**：不是，构成很有意思。两边各自**恰好丢了一道题**：图库丢的是一道开放题，SQLite 丢的是一道多跳题，各丢三分之一个检查项。然后两道负例题，**双方一起翻车**，都只拿了一半分。剩下的题，两边事实分都是满分。

**小舟**：所以结论是：图没让模型变得更「对」？

**老麦**：在这份数据里，是的——事实层面打平。图让模型变得更「省」。但我想强调：**对 Agent 来说，「省」本身就是质量的一部分。**你少写一段查询，就少一次执行出错的机会——这就是 22/23 对 21/23；你的答案短 40%，上下文窗口就能多装一轮推理；你的返回形状是子图，就不用再写一段代码去重组扁平行集。这正好对应文档里那个论点：**信息层的输出形状，直接决定了每轮推理的上下文质量。**

**小舟**：那为什么 SQL 这边就啰嗦？给我点具体的。

**老麦**：看逐题明细，模式很清楚。第一，**一道题拆成好几段 SQL**：有道 lookup 题，让列数据源加总数，图库一条 MATCH 带回名称、说明和计数，309 字符；SQLite 先来一段列表，再来一段 COUNT，最后还嫌不够，又写了个 UNION ALL 把合计行拼回结果里——三段 SQL，527 字符，第三段纯属多余。第二，**冗余列**：字段列表非要带上 dtype、size、precision、scale、order_no 一大串，题目问的其实就三列。第三，**试错和多写法**：有道过滤题，SQLite 侧一口气给了三种写法——还因为一次塞了两条语句，直接执行报错「You can only execute one statement at a time」，这就是它 21/23 里挂掉的一次。

**小舟**：我要替 SQL 说句公道话：啰嗦的另一面是探索。我看了明细，那道过滤题里，SQLite 顺手把草稿表和正式表的配对关系也查出来了——这是题目没要求、但对人真有价值的增量。

**老麦**：这个我认，而且值得说透：**发散式探索是 SQL 多查询风格的隐藏红利**，待会儿讲开放题的时候它会正式出场、甚至反杀。但按这期的评分口径——「达成目的且简洁」——多余输出不加分，只扣简洁分。另外公平起讲，图库也不是简洁的楷模：它的平均简洁度 0.599，离满分还远，有一道多跳题它也玩了三段查询外加一堆 collect 和 UNWIND 的体操，1273 字符。**两边都还有啰嗦的毛病，只是 SQL 的啰嗦是系统性的，图的啰嗦是偶发的。**

## 第六幕：分类细读——哪里赢、哪里输、哪里双输（21:00 – 25:30）

**小舟**：分题型看。差距最大的是哪类？

**老麦**：**multi_hop，多跳类，0.923 对 0.841**，六个题型里差距最大。这跟纸面推演一致：路径式问题是图的主场。里面最戏剧性的是第六题，图库满分 1.0，SQLite 只有 0.616。

**小舟**：发生了什么？

**老麦**：题目是：「哪些字段名在至少 5 个不同数据源里出现过？」标准答案是 **250 个**——注意出题口径是大小写敏感的，`ID` 和 `id` 算两个不同的字段名。图库这边，Cypher 的属性相等本来就是逐字匹配，模型照着问题原样分组，返回 250 个，对。SQLite 这边，模型写 SQL 的时候习惯性加了个 `LOWER()`，把字段名全部转小写再分组——60 行，`id` 一个名字就数出 18 个数据源。数量检查项直接丢掉。

**小舟**：呃……这锅是不是该模型背，而不是 ER 背？`LOWER()` 是模型的习惯，不是关系模型的属性。

**老麦**：说得对，我要主动承认这个解读边界：**这不是 ER 模型的原罪，是 SQL 生态里「大小写不敏感是默认文化」的习惯迁移**——很多数据库的字符串比较天然不区分大小写，模型把训练语料里的习惯带进来了。但反过来看，Cypher 的语义更「笨」：属性相等就是逐字相等，模型反而把问题翻译得更忠实，恰好贴住了出题口径。还有个细节佐证这是习惯问题：第五题，一道双向多跳题，SQLite 也用了 `LOWER()`，返回 60 行对标准答案的 19 行——只是那题的检查项只看关键字段，侥幸过关。**同一个习惯，连续两题出现，说明是系统性的。**

**小舟**：那反转的题型呢？我记得有 SQLite 赢的。

**老麦**：**open_ended，开放题，0.838 对 0.767，SQLite 反超**。这是图阵营最疼的一题。具体是第一题：「如果我要排查雇员的银行账户信息，应该重点看哪些表？」图库的答案是典型的一次大遍历：拿英文关键字——BANK、ACCOUNT、ACCT、EMP——去撞表名和字段名。结果一个 SSOP 的大宽表，一百二十七个字段几乎全命中，把结果榜霸住了，硬是漏掉了 IHRM 那边的银行卡表，检查项丢一条，只拿 0.589。SQLite 的答案是四段 SQL、多个角度，**其中一段用了中文名 LIKE『银行』『账户』**——正好把 IHRM 的表捞出来了，检查项全中，0.83。

**小舟**：所以开放题上，SQL 的笨拙发散反而赢了图的一次收敛。

**老麦**：对，这就是我说的「反杀」时刻，也是这期播客我最想让大家记住的修正：**图的优势是条件性的——问题得有形状，才谈得上对齐。**开放题没有明确的路径形状，「一条 MATCH 走天下」的思维会让模型过早收敛到单一检索角度；SQL 那种一条一条试、英文不行换中文的笨办法，覆盖面反而更广。所以别把「问题形状对齐」当成无条件碾压的定律，它是**有适用边界的**。

**小舟**：lookup、filter、aggregate 这三类呢？

**老麦**：图小胜，但要看清楚赢在哪：三类的**事实分两边全是满分**，差距全是简洁度红利。比如聚合类 0.965 对 0.908，最典型的一道题图库一条 MATCH 输出 173 字符拿满分；SQL 那边事实也对，就是答案长。顺便说一句，也不是每题都赢——第四道聚合题 SQLite 反而高一点。**总体图赢，但不是碾压，是积小胜。**

**小舟**：最后，negative，负例类。

**老麦**：**双输，0.618 对 0.61，基本没差别。**两道题特别说明问题。第一道，问一张根本不存在的表有哪些字段——两边都规规矩矩返回了空结果，都没编造字段，这点及格；但**两边都不肯把「这张表不存在」明明白白说出口**，就给你看一个空行集。第二道更惨，问「哪张表的数据行数最多」——元数据里根本没有行数这个信息。图库的模型想当然去查一个叫 row_count 的属性，图库直接抛了个 binder 异常「找不到这个属性」；退而求其次，它拿**字段数**当行数给排了个序——答非所问。SQLite 的模型，说实话觉悟更高一点，注释里写着「需在业务源库执行，非本元数据库」——判断是对的！但它紧接着写了一条带尖括号占位符的模板 SQL，直接语法报错。最后也没把「无法判断」说清楚。

**小舟**：这题的结论应该刻在墙上。

**老麦**：**防幻觉是模型和协议层的事，存储形状救不了。**你把知识库织成什么形状，都不会让模型变得更诚实。「明确说不知道」这个能力，得靠 prompt 约定、评测守门，指望换个存储引擎解决，是找错了药方。

## 第七幕：原理收拢——三个形状对齐 + 工程上的落点（25:30 – 27:30）

**小舟**：最后把观点收拢一下。你文章里的总结是「三个形状对齐」？

**老麦**：对。第一，**问题形状对齐**：路径问题对遍历查询——多跳类的成绩支持它。第二，**Agent 形状对齐**：自然查询加子图直接作上下文——总分里那 0.04 的简洁度差、输出量差 57%，就是它在数据上的投影。第三，**演化形状对齐**：Schema-free——治理需求三天一变，今天加计算口径，明天要记血缘变更历史；图里新增节点或边类型只需加标签，无 DDL 无迁移，动态属性也放得下。评测没测演化，这条目前是工程判断，不是数据结论，得说清楚。

**小舟**：工程落点呢？你最想强调的那句。

**老麦**：**图的价值不在图数据库本身，而在遍历式查询原语和子图返回形状。**所以正确的架构是把节点/边的逻辑模型和遍历查询接口当作核心资产，把存储后端当可替换实现。govio 里这个抽象叫 GraphFactory：同一套逻辑模型，底下挂过三种后端——NetworkX 做内存图、FalkorDB 做服务端 Cypher、Ladybug 做嵌入式 Cypher。今天换存储，上层 Agent 技能一行不用改。

**小舟**：还有两个你文档里的特色设计，确定性 ID 和相似度边，一句话带过？

**老麦**：确定性 ID：每个节点用业务键哈希出 10 字符的固定 ID，前缀 PT、CO、ME 区分表、列、指标——重复导入幂等，审核通过的事实才有可靠的沉淀层，来源和审核记录作为 provenance 属性挂在节点上，「这个口径的依据是什么、何时被替代」，答案就在图里。相似度边：把高置信度的语义相似对——比如 emp_id 和 employee_code——沉淀成带 confidence 的 SIMILAR_TO 边，和人工审核的 COMPLIES_WITH、DERIVED_FROM 这些「事实边」明确区分，查询时按类型过滤。这样 Agent 一次子图展开，同时拿到显式关系邻居和语义邻居——**「发现本该有却缺失的关系」，往往是治理场景最高价值的问题，这也是 ER 最难自然复刻的一点：相似度一旦变成可遍历的边，就进入了 Agent 的推理射程。**

## 收尾（27:30 – 28:30）

**小舟**：总结陈词，各一句。我先来：今天这期对我来说最大的收获不是「图好还是表好」，而是学会了看这类评测的正确姿势——**总分是会骗人的，要拆到检查分和输出量的构成**。图 0.867 对 SQLite 0.827，看着是 4 个点的胜利，拆开是「事实打平 + 省了 57% 的输出」；而开放题被反超、负例题双输这两个「输面」，恰恰框定了图优势的适用边界。选型建议我说人话：**点查为主、要强一致、问题清单固定——ER；问题是路径式的、要演化、要给 Agent 当上下文——图逻辑模型；至于模型说不说「我不知道」——那是存储层管不着的，去改你的 prompt 和守门评测。**

**老麦**：我的一句，还是文档里那句：领域 Agent 等于专门信息加技能加 Runtime，信息层是最有设计价值的一环。**信息一旦织成图，Agent 的每一次检索，就是在展开一张恰到好处的子图——这可能是「专门信息」能给领域 Agent 带来的最大杠杆。**但今天的数据也替我把后半句补上了：这张子图要「恰到好处」，前提是问题本身得是路径式的。

**小舟**：好，那就是下期的钩子了——开放题和负例题怎么救？欢迎老麦下次带着新的评测方案回来。感谢收听，我们下期见。

### 三个反直觉发现

1. **事实正确性打平（0.942 vs 0.942）**：总分差 0.04 全部来自简洁度权重；SQLite 答案平均长 57%。
2. **打平的构成是对称的**：图丢 open-01（漏 IHRM 银行卡表），SQLite 丢 hop-06（LOWER() 大小写归一，60 行 vs 250 行），负例 neg-01/neg-02 双双只得半分。
3. **图的优势是条件性的**：问题有路径形状时对齐生效（multi_hop）；无形状时可能反噬（open_ended）；诚实性与形状无关（negative）。

### 观点框架（来自 `docs/graph-first-information.md`）

- 领域 Agent = 专门信息 + 技能 + Runtime；信息层的形状是设计重点
- 治理问题本质是路径问题：查询自然度 × 返回形状（子图直接作上下文）
- ER 的真实优势：物理外键一致性、一两跳点查直白、单文件零依赖；分歧在开放多跳异质路径（递归 CTE）
- 六维度认知负荷分配：固定跳查询/异质多跳/返回形状/模型演化/一致性约束/schema 对齐成本
- 工程结论：核心资产是节点/边逻辑模型 + 遍历查询接口（GraphFactory：NetworkX / FalkorDB / Ladybug 可替换）；确定性 10 字符节点 ID（PT/CO/ME + SHA256[:8]）保证幂等导入与 provenance；SIMILAR_TO 边（带 confidence）让语义邻居进入推理射程
